Tempo execution uses an owner-exported, policy-scoped capability.

  allowit tempo import EXECUTOR_JSON
  allowit tempo execute RECIPIENT AMOUNT [--json]
  allowit tempo pay RECIPIENT AMOUNT [--json]
  allowit tempo call URL --id REQUEST_ID --max-amount AMOUNT [--json]
  allowit tempo resume REQUEST_ID [--json]
  allowit tempo submit REQUEST_ID TRANSACTION_HASH [--json]
  allowit tempo status REQUEST_ID [--json]

Configuration:
  ALLOWIT_TEMPO_BUNDLE  executor bundle (default .allowit-tempo/executor.json)
  ALLOWIT_URL           optional origin, must match the exported origin
  ALLOWIT_REQUEST_ID    explicit request identity; required for execute/pay
  ALLOWIT_TEMPO_EXECUTOR_KEY_FILE private 0600 file: 32-byte hex executor key
  ALLOWIT_TEMPO_RPC_URL           optional RPC override (chain must match)
  ALLOWIT_TEMPO_STATE_DIR         private POSIX journal base directory
                                 default $XDG_STATE_HOME/allowit/tempo or
                                 $HOME/.local/state/allowit/tempo
  ALLOWIT_TEMPO_WAIT_SECONDS      finality wait, 0..600 (default 120)
  ALLOWIT_TEMPO_MAX_GAS           gas cap, 21000..10000000 (default 1500000)
  ALLOWIT_TEMPO_MAX_FEE           total fee cap in test dollars (default 0.1,
                                 positive, at most 1, six decimal places)
  ALLOWIT_EXECUTION_ACTION        default transfer
  ALLOWIT_EXECUTION_MERCHANT      optional merchant
  ALLOWIT_EXECUTION_CONTEXT_JSON  bounded runtime context object
  ALLOWIT_CA_FILE                 optional extra PEM roots

Execute evaluates the exact policy and validates the authority-signed Tempo
wallet plan. It prints that plan, spends nothing and exits 10. The designated
executor signs and sends through its own Tempo wallet. Submit reports only
that transaction's hash; settled requires a backend-verified receipt.

Pay validates that same plan, signs one native 0x76 vault call using only the
designated executor key, and sends it directly through RPC. It persists the
complete signed transaction before sending. Confirmation requires canonical
finality, the exact token transfer and a matching settled backend operation.
No Node runtime or external payment script is needed.

Call performs one HTTPS GET, parses a real 402 Payment challenge using the
official Rust MPP SDK and applies the same native vault policy/payment pipeline.
MPP supports only Tempo testnet (42431), charge/push with client-paid fees,
one recipient and the exported token. URL must be canonical HTTPS without query,
credentials or fragment. Redirects, custom headers, splits and sponsored/pull
transactions are refused. --id and an exact six-decimal --max-amount are required.
The original URL/challenge is private and durable before authorization; the
authority-signed plan and token receipt must match the challenge-bound memo.

After finalized payment and backend settlement, call submits the hash credential
once to the same URL. It returns an escaped UTF-8 API body of at most 64 KB after
a successful HTTP status and matching Payment-Receipt. --json includes purchase
state, HTTP status, receipt and body. The body stays in the private journal;
backend history receives only an executor-attributed status, receipt, digest and
byte count. This report is not independent provider proof.

Repeating call with the same ID never fetches a replacement challenge. Resume
never authorizes or signs a new payment. A saved HTTP-attempt marker prevents
credential replay after timeout/crash; confirmed payment can therefore remain
response_unavailable (exit 5). Resume can submit the original credential once
only if no previous HTTP attempt was recorded. It returns a cached successful
response on later recovery (exit 6). After owner input, rerun the original call
with the same URL, ID and maximum if no signed transaction exists.

Resume checks the original signed transaction without reading a key, obtaining
another authorization or signing a replacement. It first checks the saved
hash. If that transaction is absent, it may rebroadcast only the exact saved
bytes with the same hash and account nonce. A missing receipt remains
pending/uncertain. Keep the same journal, bundle, request ID and exact intent;
do not create a new request or erase its journal after an uncertain outcome.

Use Linux/WSL and keep keys/journals on its Linux filesystem. Pay serializes all
vaults sharing an executor and chain in one journal. Use that same journal for
every process and keep this executor dedicated to these payments. The executor
needs fee-token funds of its own; vault funds pay the authorized recipient.
Only testnet/localnet is supported. No mainnet or legacy transaction fallback.

Never give the agent a server authority key. Owner lifecycle operations stay
in the browser. Import/execute/submit/status never read an executor key;
pay reads only the executor key; no command reads an owner or authority key.
Preserve the same request ID and exact intent after an uncertain outcome.

Exit codes: 0 imported/settled, 2 usage, 3 configuration, 5 uncertain,
6 already-settled replay,
10 wallet plan prepared, 11 awaiting owner input, 12 submitted, 20 denied/failed.
